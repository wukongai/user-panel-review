# ADR-0001：公开核心与私人 Audience Workspace 分离

状态：Accepted  
日期：2026-08-15

## 背景

`user-review` 0.3 把公共 Persona 和可写长期 Persona 都放在 Skill 源目录。这个结构适合演示，但不适合开源产品：安装目录可能在更新时被替换；私人画像可能被误提交；同一用户在多个内容项目中会产生多份副本；调用项目会被错误地当成画像数据所有者。

同时，为每种内容类型分别维护画像库会导致同一用户在文章、销售页和落地页之间复制、漂移，破坏长期用户认知的积累。

## 决策

1. `wukongai/user-review` 是唯一代码事实源和独立产品，不依赖 Content Factory。
2. 公共仓库内的示范 IP 和内置 Persona 为只读资产。
3. 私人长期画像由 `user-review` 管理在独立用户数据目录，默认是 `~/.user-review/workspaces/<id>/`。
4. 一个 Audience Workspace 对应一个相对稳定的 IP、企业品牌或产品线。
5. 同一 Workspace 的 Persona 跨内容类型复用；不同内容只改变 Stimulus、场景 Panel 和研究协议。
6. 修改内置 Persona 必须派生到私人层，不允许覆盖或同 ID shadow。
7. 所有私人长期变更采用不可变 Preview / Apply 计划、影响分析、备份和 Change Record。
8. 上层 Content Review 或任意内容项目只能调用 `user-review`，不得拥有或复制画像库。

## 备选方案

### A. 每个调用项目保存一份画像库

优点是路径直观；缺点是跨项目重复、升级和同步困难，并让 Content Factory 等调用者变成错误的事实源。拒绝。

### B. 私有仓为事实源，每次脱敏导出公开仓

第一次从私有能力抽离公开项目时必要；长期会造成两套代码、双倍测试和行为漂移。拒绝作为持续维护模型。

### C. 所有数据写进已安装 Skill

开箱简单，但更新覆盖、权限、隐私和多安装副本冲突不可接受。拒绝。

### D. 公开只读核心 + User Review 私人数据目录

既保留开箱即用示范，又保护用户数据，并允许跨文章和跨调用项目复用。采用。

## 后果

正向后果：

- 用户无需 Content Factory 或项目级 Skill 副本；
- 更新代码与维护画像相互独立；
- 同一受众系统能跨文章、销售页和后续刺激物复用；
- 私人数据不会进入公共 Git 历史；
- 画像变更可以审计、备份和恢复。

代价：

- CLI 和 Agent 必须解析 Skill 根目录与用户数据目录两个来源；
- 需要 workspace schema、迁移和冲突检测；
- 远程安装回归必须验证重装后数据仍在；
- 公共 Persona 不能原地修改，需要“派生”这一明确概念。

## 不改变的边界

本 ADR 不引入 Expert Review、专业方法、交互式可用性、真实用户研究或效果预测，也不授权把私人画像上传到任何远程服务。
