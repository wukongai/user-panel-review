# user-review 画像系统与仓库改名设计

状态：已确认，待实施  
日期：2026-08-14  
目标版本：0.3.0

## 1. 背景与问题

当前 `user-panel-review` v0.2 同时承担两类不同职责：

1. 由普通目标用户 Persona 组成焦点小组，表达阅读感受；
2. 使用传播学等专业方法和专业评审者诊断文章。

这使用户评审与专家评审混在同一个 Skill 中，也把某个外部方法名称暴露成产品主概念。新版本必须恢复清晰边界：用户评审只模拟目标用户焦点小组；专业方法属于未来独立的专家评审 Skill。

## 2. 名称与产品边界

名称固定为：

- `user-review`：用户焦点小组评审；
- `expert-review`：未来的专家方法评审；
- `article-review`：未来统一调用两者并汇总的文章评审入口。

本版本只实现并发布 `user-review`。`expert-review` 和 `article-review` 不在本次创建范围内，避免未设计完整时产生空壳仓库。

仓库从 `wukongai/user-panel-review` 改名为 `wukongai/user-review`。Skill 目录、元数据、命令示例、测试和文档全部使用 `user-review`。

## 3. user-review 的职责

`user-review` 的唯一核心是：根据文章和目标受众组成一个可追溯的模拟焦点小组，让互相隔离的 Persona 分别阅读文章，再汇总共识、分歧与少数意见。

它可以有稳定的焦点小组执行协议和证据规则，但不得包含领域专家方法包、理论量表或专业评审角色。

必须删除：

- `propagation-dbs-v1` 及方法目录、方法目录表和方法选择参数；
- `professional_reviewer`、`professional_risks`；
- `method_observations`、`method_findings`、`theory_basis` 等专家方法字段；
- README 和用户手册中对 DBS、传播方法论、专业评审者的宣传与示例。

## 4. 三层画像体系

### 4.1 长期画像库 Persona Library

保存可以跨文章复用的 Persona。用户可以用自然语言新增、查看、修改、停用画像。每个画像至少包含：

- `id`、`version`、`name`、`summary`；
- 适用领域、内容类型、平台与阅读场景；
- 与内容的关系：核心用户、邻近用户、挑战用户或非目标用户；
- 认知阶段：未意识、已意识、寻找方案或已有经验；
- 用户任务、痛点、信任信号、拒绝信号、语言线索；
- 来源、置信度、验证状态和生命周期状态。

画像描述必须基于内容关系、任务和行为线索，不得依赖刻板人口属性，也不得推断敏感身份。

### 4.2 内容映射 Audience Map

内容映射保存“某类内容通常需要哪些画像”的多对多关系。映射依据包括内容领域、文章目标、内容类型、平台、受众阶段和理解门槛。

映射不是永久固定名单。同一个 Persona 可以服务多个内容线；同一内容线也可以有多个候选 Persona。

### 4.3 单次评审团 Run Panel

每次评审建立不可变的 Persona 快照，来源可以是长期画像库，也可以是只用于本次文章的临时画像。修改长期画像不能改变已经开始的评审。

新画像默认只在本次运行中生效。只有用户明确说“保存到画像库”或确认保存预览后，才写入长期画像库，防止一次性假设污染长期资产。

## 5. 自动组团流程

1. 读取文章、用户声明的目标和已有受众信息；
2. 识别内容领域、文章目标、内容类型、平台、认知门槛；
3. 从内容映射和画像库中提出候选 Persona，并解释每个入选原因；
4. 检查是否覆盖核心用户、必要的邻近用户和能暴露盲点的挑战视角；不为凑类型强行加入无关 Persona；
5. 如果现有画像无法覆盖关键受众，生成一个本次运行临时画像并明确标记；
6. 在运行前预览评审团、画像来源、覆盖理由和写入位置，允许用户增删或替换；
7. 固化文章哈希和 Persona 快照，再让多个隔离 Worker 独立评审；
8. 评审结束后，可以建议把有长期价值的临时画像保存到画像库，但必须再次获得明确确认。

自动选择可以使用确定性匹配与可解释的排序，但不得向用户展示无法解释的神秘总分，也不得把模拟反馈伪装成真实用户研究。

## 6. 焦点小组输出

每个 Persona 输出：

- 第一反应；
- 与自己的相关性；
- 阅读摩擦与难懂处；
- 信任或怀疑的触发点；
- 希望保留的内容；
- 自然产生的问题；
- 可能采取或拒绝采取的下一步；
- 原文证据锚点；
- 限制与不确定性。

汇总报告输出：

- 共识；
- 分歧；
- 少数意见；
- 战略性非目标拒绝；
- 必须保留的内容；
- 后续真实用户验证假设；
- 失败 Worker、法定人数和证据限制。

报告必须持续标注“模拟用户反馈”，不得预测点击率、转化率或真实市场结果。

## 7. 兼容与迁移

这是 pre-1.0 阶段的破坏性边界修正，版本升级为 `0.3.0`。

- GitHub 仓库改名后使用平台重定向兼容旧 URL；
- 新仓库只暴露 `user-review`，不同时暴露两个可触发 Skill，避免路由冲突；
- 已安装旧版的用户需要移除 `user-panel-review`，再安装 `user-review`；
- 用户手册提供完整迁移命令和行为差异；
- 历史 Changelog 保留旧版本事实，但标记 v0.2 方法层已被 0.3.0 撤回；
- 旧的专家方法材料不迁入 `user-review`。未来 `expert-review` 必须重新确认来源、命名和许可边界后独立实现。

## 8. 用户手册范围

中文版用户手册必须覆盖：

- 安装与从旧名称迁移；
- 第一次评审；
- 自动选择 Persona 的依据；
- 临时新增 Persona；
- 明确保存到长期画像库；
- 查看、修改、停用 Persona；
- 管理内容映射；
- 调整单次评审团；
- 解读共识、分歧与少数意见；
- 模拟研究边界和隐私边界。

## 9. 验收标准

1. 仓库、Skill、目录、元数据和主要命令统一为 `user-review`；
2. Skill 中不存在 DBS、方法包、专业评审角色及其输出字段；
3. 用户可以预览并管理长期画像库、内容映射和单次评审团；
4. 临时画像默认不落库，明确确认后才可保存；
5. 文章与 Persona 在运行前形成不可变快照；
6. 多 Persona 隔离、法定人数、部分失败与证据锚点能力继续通过回归；
7. README、用户手册、Changelog、版本、测试和 CI 一致；
8. 从改名后的远程仓库完成干净安装和一篇文章的完整用户体验回归；
9. 不把真实文章、临时运行工件、凭证或完整会话提交到公开仓库。
